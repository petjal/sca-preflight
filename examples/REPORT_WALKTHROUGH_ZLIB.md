## 3. Four Practical Takeaways From That Gemini Run

Looking closely at the `madler/zlib` report and Gemini's summary highlights four questions that come up in real DevSecOps pipelines:

### Takeaway A: How Did `sca-prescan` Map Those Two CVEs to `zlib` Without a Package Manager or Internet Connection?
- Pure C repositories like `madler/zlib` have no `package-lock.json`, `pom.xml`, or `Cargo.lock`. Standard package-manager detectors return `0` components on them.
- `sca-prescan` caught and code-verified both CVEs in three **100% offline** steps:
  - **Step 1 (C Version Header Extraction on Disk)**: While walking the file tree (`dpi.py`), whenever `sca-prescan` sees a C/C++ version header (`zlib.h`, `opensslv.h`, `curlver.h`, `expat.h`, `sqlite3.h`, or OpenSSL 3.x `VERSION.dat`), it parses the version macros directly from the file bytes (`_parse_c_version_header_bytes`). In `zlib.h`, it extracted `#define ZLIB_VERSION "1.2.11"`, mapped the `ZLIB_` macro prefix to component `"zlib"`, and recorded `internal_manifest:zlib.h` (`zlib 1.2.11`).
  - **Step 2 (Offline Version-Range Match Against `pareto_vuln_kb.json`)**: Next, `vuln_matcher.py` compares every discovered `(component, version)` pair (`("zlib", "1.2.11")`) against `sca-prescan`'s built-in offline JSON catalog (`3,910` CISA-KEV, 2025-2026 hot/pre-NVD, and CVSS 9.8-10.0 rules). Because `1.2.11` falls inside `>=1.2.0,<1.2.12.1` (`CVE-2022-37434`, CISA-KEV) and `>=1.0.0,<1.3.1` (`CVE-2023-45853`), both rules matched immediately with **zero outbound network queries**.
  - **Step 3 (Unpatched Code Snippet & Shaded-Bytecode Verification)**: What if `zlib.h` had been stripped, or a Java/Go dependency was shaded into an uber-JAR with `META-INF/maven` deleted, or a version string was hidden behind an unresolved `${...}` corporate parent POM property, or a Linux distro backported the security fix into `1.2.11` without bumping the version string? `sca-prescan`'s **Snippet & Shaded-Bytecode Engine** (`snippet_signatures.json`) inspects target source files and in-memory `.class` bytecode constant pools directly (`vulnerable_anchor_regex` PRESENT + `patch_guard_regex` ABSENT). On `madler/zlib`, the snippet engine verified that `inflate.c` lacks the upstream `len < state->head->extra_max` guard (`[UNPATCHED-SNIPPET-VERIFIED: unpatched code in inflate.c]`) and `contrib/minizip/zip.c` lacks the `size_filename > USHRT_MAX` guard (`[UNPATCHED-SNIPPET-VERIFIED: unpatched code in contrib/minizip/zip.c]`). Conversely, if the upstream security guard is present in an older version string, the engine flags `[PATCH-GUARD-DETECTED]`.

### Takeaway B: "Doesn't Detect Come With Its Own Java?"
- **Why this trips people up**: Black Duck has **two separate Java processes** during a scan, and only one of them bundles Java:
  - **The Signature Scanner (`scan.cli.zip` / `scan.cli.sh`) DOES bundle its own Java (`jre/` folder)**: Once Detect is running, it downloads `scan.cli-<version>.zip` from your Black Duck server into `~/blackduck/tools/Black_Duck_Scan_Installation/`. Inside that zip is a private `jre/` directory that the Signature Scanner uses.
  - **The Detect Bootstrapper (`detect10.sh` / `detect11.sh` / `detect.jar`) does NOT bundle Java**: `detect.jar` is a standalone Spring Boot `.jar` file. The `detect10.sh` shell script looks for a host `java` binary (Java 11, 17, or 21) on `DETECT_JAVA_PATH`, `JAVA_HOME`, or `PATH` just to launch `java -jar detect.jar`.
- **What happens in C/C++, Go, Rust, or Python CI containers**: Engineers know `scan.cli.zip` has an embedded JRE, so they run `detect10.sh` inside a minimal C/C++ or Go build container that has `gcc` or `go` installed but no host Java. `detect10.sh` immediately fails before it can even download `scan.cli.zip`.

### Takeaway C: Why Did the First Report Flag `512 MB RAM` and `Missing Java`? (CI Runner Mode vs. `--repo-only` Mode)
- By default, `sca-prescan` is designed to run **inside your actual CI build container** right before `detect.jar` runs. So it inspects both the **repository files** and the **host container environment** (`/sys/fs/cgroup/memory.max` RAM limits and host `java` availability).
- Because we ran the initial blind challenge inside our own locked-down **512 MB RAM quarantine sandbox** on a Linux machine without Java installed, `sca-prescan` faithfully reported that the 512 MB sandbox container was too small to run the Detect JVM (`2,560 MB` minimum required) and lacked a host Java runtime.
- Passing `--repo-only` instructs `sca-prescan` to evaluate only the repository files on disk and assume a standard CI runner (`4,096 MB` scanner memory, host Java present).

### Takeaway D: Why Did a Pure C Library Trigger `unpinned_manifests_count: 1` and `--detect.detector.search.depth=3`?
- At first glance, `zlib` is a classic C library with a `Makefile` and `CMakeLists.txt` - why did `sca-prescan` count `1` unpinned package manifest at depth `3` and warn about `--detect.accuracy.required=ALL`?
- Because buried three folders deep inside `madler/zlib` is `contrib/dotzlib/DotZLib/DotZLib.csproj` (a legacy C# wrapper for `zlib1.dll`).
- Under Default Detect (`--detect.detector.search.depth=0`), `DotZLib.csproj` is **silently ignored**. Conversely, if you opt into `--detect.detector.search.depth=3` on a C build machine without the `.NET` SDK installed, Detect's NuGet detector discovers `DotZLib.csproj`, fails to run `dotnet`, and aborts the entire pipeline with **Exit Code 5 (`FAILURE_DETECTOR`)** or **Exit Code 15 (`FAILURE_ACCURACY_NOT_MET`)** unless you also pass `--detect.accuracy.required=NONE` or `--detect.excluded.detector.types=NUGET`.

## 4. Complete File & Byte Disposition Accounting (`Bucket 1 + 2a + 2b + 3`)

### 4.1 Why Standard Scanner Logs Leave You Guessing
Even if you run Black Duck Detect with `--logging.level.com.synopsys.integration=DEBUG`, the log only prints detector entry points where a `Detectable` matched a known filename rule at the current search depth. It **never** gives you a conservation-of-mass table showing:
- Which folders were skipped before traversal (`Bucket 1`)
- Which files actually drove BOM expectations, version extraction, CVE/license hits, or CLI flag calibration (`Bucket 2a`)
- Which files were hashed for source provenance only (`Bucket 2b`)
- Which actionable files on disk were **silently ignored** or **silently corrupted** by Default Detect settings (`depth=0`, `UTF-8` parser assumption, `individualFileMatching=NONE`).

Every `sca-prescan` report now enforces strict conservation of mass across four mutually exclusive buckets (`Bucket 2a + Bucket 2b + Bucket 3 == total_files_scanned`):
- **Bucket 1 (Excluded Non-Shipping Directories)**: Folders we saw on disk (`.git`, `.venv`, `venv`, `__pycache__`, or `node_modules` when a sibling lockfile exists), skipped traversing, and added to `--detect.excluded.directories`.
- **Bucket 2a (Actionable BOM, Vuln & Calibration Files - Layer 1 / `L1`)**: Every file we both hashed into `L1` and actively parsed (`2a-i` Lockfiles & Manifests, `2a-ii` C/C++ Version Headers & Native Build Scripts, `2a-iii` Archives & Compiled Binaries, `2a-iv` Legal / SPDX / Container files). Every file in `Bucket 2a` is listed row-by-row in the report ledger.
- **Bucket 2b (First-Party Source & Doc Provenance Only - `L2 - L1`)**: Regular `.c`, `.h`, `.py`, `.java`, and `.md` files that contain no third-party dependency declarations. Hashed into Layer 2 (`L2`) and checked for embedded private keys.
- **Bucket 3 (Unhashed Beyond Monorepo Early-Stop Cap)**: Files in massive monorepos (`> 5,000` files) where `L2` content hashing stopped early so CI never hangs (while `L0` and `L1` still cover 100%).

## 5. Field-by-Field Legend: How Every Line Is Calculated & What Values to Expect

### 5.1 What "Scanned" Means (`total_dirs_scanned`, `total_files_scanned`, `total_workspace_mb`)

When the report header says `total_dirs_scanned: 40`, `total_files_scanned: 254`, and `total_workspace_mb: 2.85`, `sca-prescan` did **not** just run `find . | wc -l`. Across those 254 files, it executed **four distinct offline passes**:
- **Pass 1 (Directory, Manifest & Encoding Walk)**: Walked all 40 non-excluded directories and 254 files (`2.85 MB`), classified lockfiles vs. unpinned manifests (`DotZLib.csproj`), checked manifest byte encodings (`UTF-8` vs `UTF-16LE/BE` BOMs that break standard UTF-8 parsers), and measured the exact directory depths needed for `--detect.detector.search.depth`, `--detect.binary.scan.search.depth`, and `--detect.excluded.directories.search.depth`.
- **Pass 2 (In-Memory Archive, Binary & Header Inspection)**: Opened archives (`.jar`, `.war`, `.whl`, `.tar.gz`, `.zip`, `.deb`, `.rpm`) and compiled binaries (`.so`, `.dll`, `.exe`) in memory without extracting files to disk, scanned class paths for shaded uber-JAR blind spots (`JndiLookup.class`), extracted ELF/PE/Mach-O binary version strings, parsed C/C++ version headers (`zlib.h`, `opensslv.h`, `VERSION.dat`, `curlver.h`), and inventoried legal/SPDX attribution files (`LICENSE`, `README`, `NOTICE`).
- **Pass 3 (3-Layer Cryptographic Provenance Hashing)**: Hashed all 40 directory skeletons (`L0`, zero file reads), 100% of the 11 dependency-bearing inputs (`L1` / `Bucket 2a`), and all 254/254 files (`L2`, `100.0%` coverage).
- **Pass 4 (Offline Version-Range & Rugpull Matching)**: Checked all discovered `(component, version)` pairs offline against `pareto_vuln_kb.json` and `pareto_license_kb.json` (`0` outbound network calls).

### 5.3 How Section 2 Separates Vendor Default Policy from Optional Tweaks (and Handles Additive Merging)

Black Duck's stated best-practice policy is to **run Detect with default settings first** (`--detect.tools=ALL`, `--detect.detector.search.depth=0`) for predictable scan speed, and treat deeper searches (`depth > 0`, `search.continue=true`, `individualFileMatching=BINARY`) as deliberate opt-in trade-offs that expand BOM completeness at the cost of longer scan times.

To respect that policy and avoid nagging teams about flags they already set:
- **Section 2.1 (Baseline Safe Invocation)**: Gives the conservative command line that keeps Detect's default `depth=0` and `tools=ALL` behavior while adding only safe runner memory sizing (`--detect.blackduck.signature.scanner.memory`), `.git`/`.venv` exclusions (`--detect.excluded.directories`), and the Project Version Notes provenance stamp (`--detect.project.version.notes`).
- **Section 2.2 (Optional Fuller-BOM & Buildless Tweaks)**: Lists opt-in flags (`--detect.detector.search.depth=3`, `--detect.detector.search.continue=true`, `--detect.blackduck.signature.scanner.individual.file.matching=BINARY`, `--detect.gradle.excluded.configurations=...`) in a separate table that explains both **what hidden files they unlock** in this specific repo and **what performance trade-off they carry**.
- **Section 2.3 (`--existing-detect-args` Additive Concatenation & Noise Suppression)**: If your CI pipeline already passes Detect flags (for example, `--existing-detect-args "--detect.excluded.directories=build,third_party --detect.detector.search.depth=3"`), `sca-prescan` automatically:
  - **Additively concatenates** comma-separated flags (`--detect.excluded.directories=build,third_party,.git`) so your existing exclusions are never overwritten.
  - **Suppresses duplicate recommendations** for flags your pipeline already sets at or above the required value.
